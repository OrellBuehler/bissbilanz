# Bissbilanz — Full Codebase Review (2026-06-17)

**Scope:** Backend (TS), Frontend (SvelteKit/Svelte 5), KMP shared (Kotlin), Android (Compose), iOS (SwiftUI), plus a cross-cutting security pass.
**Method:** 11 read-only review agents (a cleanliness/duplication reviewer + a bug-detection reviewer per area, plus one security reviewer). **No code was changed** — this is a report for triage.
**Commit reviewed:** `8cc0272b` (main, after merging origin's 9 commits incl. on-device analytics + iOS App Intents).

> Severity legend: **Critical** = data loss / security / wrong data for all users · **High** = clear bug on a common path or major maintainability hazard · **Medium** = edge-case bug or notable duplication · **Low/Nit** = minor.
> Confidence (bugs): H/M/L = how strongly the agent verified it.

---

## 1. Executive summary

The codebase is in **good overall health**: a deliberate shared error/auth layer on the backend, a real offline-first service architecture on the web, a clean OpenAPI-generated DTO layer in KMP, a **cross-language golden-vector parity test** for analytics, and a **strong security posture** (PKCE-correct OAuth AS, hashed/rotated tokens, platform secure storage on mobile, clean SAST/dependency scans). No dead code or debug leftovers in most areas.

The findings cluster into a small number of **cross-cutting themes** that each surface in 2–4 areas — those are the highest-value fixes because one decision resolves many sites. The single most important correctness/security item is an **IDOR-by-reference** that two independent agents (backend-bug + security) found and verified against the code.

### Must-fix (Critical/High, correctness or security)

1. **IDOR: cross-user food/recipe reference** in entries + recipes + MCP `log_food`. _(security + backend-bug, both H)_
2. **Optimistic entry create double-counts macros (value × servings²)** and the wrong value persists offline. _(frontend-bug, H)_
3. **Offline create/update of foods & recipes can double-enqueue → duplicate server records.** _(frontend-bug, M-H)_
4. **Pending offline writes never sync on app startup** (only on an offline→online transition). _(frontend-bug, H)_
5. **Locale comma-decimal input silently dropped/corrupted** — web, Android, and iOS numeric fields. _(frontend + android + ios bug, H)_
6. **Food merge re-points historical entries without rescaling `servings`** → silently changes past days' macros. _(backend-bug, M-H)_
7. **On-device analytics diverge from server** in functions _not_ covered by the parity suite (calorie front-loading, TEF%, weight smoothing, caffeine cutoff). _(kmp-bug, H)_

### Biggest maintainability levers (cleanliness/duplication)

- **"Abstraction exists but is applied inconsistently"** — the recurring shape in _every_ area (`withAuthedResource`, the `Result` pattern, `InsightCard`, `base.ts`, the offline-first repo pattern, `CardView`, `WidgetMacroRing`).
- **No shared number/macro formatting layer** anywhere — rounding/units/locale re-implemented at every leaf on web, Android, and iOS (also the root cause of theme #5).
- **Cross-language duplication of nutrition science** (RDA/DII/TDEE constants + algorithms) in Kotlin _and_ TS — deliberate, parity-guarded, but the constants should be code-generated from one source.
- **i18n half-adopted** on Android and iOS (and a few web pages) — large parts of both mobile apps are untranslatable despite shipping en+de.

## 2. Cross-cutting themes (fix once, resolve many)

### Theme A — IDOR by foreign-key reference _(Critical/High; security + backend)_

`createEntry`/`updateEntry`, `createRecipe`/`updateRecipe`, and the MCP `log_food` handler accept a client-supplied `foodId`/`recipeId` and insert it **without verifying ownership**; the read-back `leftJoin`s `foods` scoped only by the _entry's_ `userId`, not `foods.userId`. An authenticated user who knows/guesses another user's food UUID can read that food's name + full macro/nutrient profile.

- Write sites: `src/lib/server/entries.ts:142-160`, `:197-201`; `src/lib/server/recipes.ts:88-96`, `:163-170`; `src/lib/server/mcp/create-handlers.ts:275`.
- Leaky read joins: `entries.ts:114-118` (recipe-macros CTE _is_ correctly scoped at `:55`, so recipe leakage is name-only).
- Validation only checks UUID shape: `validation/entries.ts:6-7`; FK enforces existence only: `schema.ts:191`.
- **The correct pattern already exists** in `supplements.ts:42-52` (`resolveIngredientFoodId`) and `food-merge.ts:136`.
- Disclosure is of _food/nutrition definitions_ only — not credentials, not the victim's own logs. Mitigated by random UUIDv4 ids. Still cross-tenant data exposure → treat as High/Critical.
- **Direction:** verify each referenced id belongs to the caller before insert; add `eq(foods.userId, userId)` to read-side joins as defense-in-depth; consider DB row-level security.

### Theme B — Locale comma decimals silently dropped _(High; frontend + Android + iOS)_

Every platform parses user-typed numbers with a locale-insensitive parser while showing a decimal keyboard. German (a first-class locale) emits `,`, which becomes `NaN`/`nil`/truncated → silent data loss or a save that no-ops with no error. **Each team already fixed it in a few spots and left it unfixed in others**, proving it's unintended.

- Web: `QuickFoodEntry.svelte:37-52`, `EditEntryModal.svelte:75-119` (`if(!cal)` silent return), `AmountInput.svelte:48-54` (`parseFloat("1,5")→1`).
- Android: `EntryEditSheet.kt:258`, `FoodEditSheet.kt:107-142`, `AddFoodSheet.kt:180`, `WeightWidget.kt:96,110`, `MealPickerSheet.kt:81`, `SupplementEditSheet.kt`, `RecipeEditSheet.kt:325-347` — vs the _correct_ `.replace(',','.')` in `WeightScreen.kt:409,454`, `QuickWeightActivity.kt:151`.
- iOS: `QuickEntrySheet.swift:89-93`, `FoodEditSheet.swift:179-200`, `WeightView.swift:791,799`, `RecipeEditSheet.swift:140-148`, `RecipeListView.swift:268` — vs the _correct_ locale-aware `NutritionLabelParser.parseDecimal` (`:202`).
- **Direction:** one locale-tolerant parse helper per platform, applied to every user-typed numeric field. Pre-filled values already emit `.`, so round-trips are safe.

### Theme C — `today()` is the UTC date, not the user's local day _(Medium; backend + frontend + KMP)_

`new Date().toISOString().slice(0,10)` (and the Kotlin equivalent) yields the UTC calendar date, used for default log date, `isToday`, streaks, and MCP date defaults. The whole stack is intentionally UTC-anchored, so it's _consistent but shifted_: for the primary CET/CEST audience it's wrong for the 1–2 h after local midnight; for any user behind UTC it's wrong every evening.

- `src/lib/utils/dates.ts:9` (+ consumers in `stats.ts`, MCP `create-handlers.ts:277,418,569`, supplement-log default).
- Note: hour-of-day analytics are _also_ timezone-inconsistent across modules (see Theme G). `analytics.ts:325` hardcodes `Europe/Berlin`.
- **Direction:** decide one timezone policy (likely the user's tz, already known for analytics) and apply it server + client + shared.

### Theme D — Offline / optimistic-write data integrity _(Critical/High; frontend)_

The web offline layer has three issues that can corrupt or lose user data:

- **Macro double-count:** optimistic entry rows store `calories = perServing × servings` while every consumer multiplies by `servings` again → `value × servings²`; offline it persists. `entry-service.svelte.ts:67-91,148-193`.
- **Double-enqueue:** `apiFetch` returns a synthetic `200 {queued:true}` offline (doesn't throw), but `withOfflineFallback` only enqueues in `catch`; food/recipe services then `db.put(undefined)` which rejects → second enqueue → **duplicate server records**. Weight/sleep guard with `isQueued(response)`; food/recipe/goals/supplement don't. `base.ts:54-66` + `api.ts:11-32` + `food-service.svelte.ts:136-168`.
- **Startup never drains the queue:** `syncQueue()` only runs on the `window 'online'` event, which doesn't fire if the app loads already-online → offline writes can sit unsent indefinitely. `stores/sync.ts:142-149`.
- **Direction:** store per-serving values optimistically; add `isQueued` early-return to all write paths (or make `withOfflineFallback` queued-aware); call `syncQueue()` on mount + on focus/visibility.

### Theme E — On-device analytics ↔ server parity gaps _(High/Medium; KMP + backend)_

The parity-locked core math (maintenance, adaptive TDEE, moving average, nutrient aggregation, Pearson correlation, RDA) **matches** server TS and is guarded by golden vectors. But several functions have **no golden vector** and genuinely diverge:

- **Calorie front-loading hour:** Kotlin parses UTC wall-clock substring, TS uses `Date.getHours()` (device-local). `CaloriePatterns.kt:24` vs `calorie-patterns.ts:22-24`. _(H)_
- **Food-quality TEF%:** Kotlin = ratio-of-averages, TS = average-of-ratios. `FoodQuality.kt:266-268` vs `food-quality.ts:229-237`. _(H)_
- **Weight moving-average:** three incompatible window definitions (iOS index-based, web 7-row, insights 7-calendar-day). `WeightChartAnalytics.kt:34-44` vs `Aggregation.kt:442-474` vs `weight.ts:81-109`. _(H)_
- **Caffeine cutoff hour** (same tz split, `CaffeineSleep.kt:43-44`), **weight projection x-axis** (index vs day-offset on iOS), **same-date weight collapse** (order-dependent), **meal-timing rounding** (`toInt` vs `Math.round`). _(M/L)_
- Web client also has its own tz inconsistency: `caffeine-sleep.ts:30` / `calorie-patterns.ts:23` use local `getHours()` while `meal-timing.ts` uses UTC `parseLocalMinutes`. _(see Theme G)_
- **Direction:** pick one canonical definition per function, route all platforms through it, and **extend the parity fixtures** to cover the weight-chart family, calorie-patterns, food-quality, caffeine-sleep.

### Theme F — Cross-language duplication of nutrition science _(High maintainability; KMP + backend)_

Large constant tables + algorithms exist in **both** Kotlin (`mobile/shared/.../analytics/*.kt`) and TS (`src/lib/analytics/*.ts`, `src/lib/utils/maintenance.ts`): RDA table, DII coefficients/means/SDs, NOVA/omega/TEF thresholds, energy densities (7700/1800, 0.3), TDEE clamps, Pearson + lgamma (~100 LOC mirrored). Deliberate (on-device analytics) and parity-guarded for _behavior on fixtures_ — but constants not exercised by a vector can drift.

- **Direction:** code-generate the shared _constants_ from one source (like the existing OpenAPI pipeline); ensure every duplicated constant is covered by a golden vector.

### Theme G — No shared number/macro/color formatting layer _(High cleanliness; frontend + Android + iOS)_

Rounding, unit suffixes (`g`/`kcal`/`kg`), and the macro color coding are re-implemented inline at every render site on all three UI platforms, with inconsistent rounding-vs-truncation and locale handling.

- Web: `Math.round`/`toFixed` across 40+ files; 4 overlapping rounding utils (`number.ts#round2`, `nutrition.ts#roundTotals`, `round-nutrition.ts`); macro Tailwind class triples hardcoded in 40+ components (`colors.ts` only has hex). 53 `text-{green,red,amber}` hits in analytics alone.
- Android: `roundToInt()`/`String.format(Locale.US,…)` everywhere though `shared/.../util/FormatUtils.kt` (`formatNutrient`, `toDisplayString`) exists; macro hex re-declared outside `Theme.kt`; `dynamicColor=true` (`Theme.kt:49`) overrides the brand macro palette on Android 12+.
- iOS: three competing "trim the .0" helpers (`NutrientRow.swift:20`, `FoodEditSheet.swift:183`, `WidgetStrings.swift:87`); `Int(...)` truncation vs rounding; hardcoded `cal`/`kg` suffixes.
- **Direction:** one formatting utility per platform + macro color/label/unit expressed as data once (`MacroValue`/`MacroChip`/`MacroSummaryRow`); treat theme tokens as the single source of truth.

### Theme H — "Abstraction exists but isn't adopted everywhere" _(Medium cleanliness; every area)_

- Backend: `withAuthedResource` used in 4/8 `[id]` routes; the `Result`/`safeParse` create/update block hand-rolled in 10 services; `res*` OpenAPI helpers done for responses but not params.
- Frontend: `InsightCard` has no `loading` prop so 20+ cards re-implement the skeleton; `base.ts` offline helpers bypassed by ~half the services; typed `api` client bypassed by analytics `fetch()` wrappers.
- KMP: no `OfflineFirstRepository` base — the cache-flow/refresh/optimistic-create/coalesce pattern is hand-written in 6 repos; `"temp_"` literal in ~18 sites despite two private `TEMP_PREFIX` consts; two separate `Json` configs.
- Android: ~14 screens inject repositories and run try/catch+snackbar **inside composables**, bypassing the ViewModel layer that exists for some of them; `clearSnackbar()` duplicated in 7 VMs.
- iOS: `CardView` defined privately inside `InsightsView` while ~8 views inline its chain; `WidgetMacroRing` exists but two widgets redraw the ring anyway.
- **Direction:** finish each migration; promote shared components out of single-file scope.

### Theme I — i18n half-adopted on mobile _(High; Android + iOS, + a few web pages)_

- Android: only the Insights subtree + a few widgets use `stringResource`; Dashboard, DayLog, Settings, FoodDetail, Weight, Supplements, Recipes, all edit sheets, nav tab titles, and content descriptions are hardcoded English (~44 string keys total). `Screen` sealed class holds raw titles.
- iOS: `ErrorView`/`LoadingView` (app-wide) unlocalized; sheet field labels, picker titles, widget gallery copy (`localeCode=="de"` ternaries) bypass `L10n`; meal-name mapping duplicated in `L10n.mealName` + `WidgetStrings.mealName` and already drifted ("Snacks").
- Web: `privacy/+page.svelte` (98 lines English), `settings/mcp`, `oauth/consent`, `login` page bypass Paraglide; a few inline `<svg>` icons and Unicode-arrow "icons" (`AdaptiveTDEECard.svelte:30-34`) violate the Lucide rule.
- **Direction:** sweep literals into resource files; add a lint rule (Android `HardcodedText`) to prevent regression.
